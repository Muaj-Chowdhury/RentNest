# Taste
- Communicates by highlighting a specific symbol/line in the IDE and asking for a conceptual walkthrough (e.g. "explain X how does it work and the flow"), so prefers thorough, step-by-step explanations that trace the call flow and reference exact file:line locations rather than short one-line answers. Confidence: 0.8
- Wants jargon-free explanations: after receiving a technically accurate but terminology-heavy explanation, replied "I didn't understand the terms and the processes." Structure answers as (1) the plain-words version of the problem first, (2) a glossary defining each specialized term (build, bundler, compiler, ESM, entry point) in everyday language, (3) the numbered sequence of what actually happened, and (4) why the fix works — avoiding unexplained acronyms and tool names. Confidence: 0.7
- When asking about code, wants the full picture: distinct scenarios/branches, the data flow end-to-end, and the rationale for decisions (e.g. "what should each return carry and how do I know"), not just a description of what the code literally does. Confidence: 0.7
- Explicitly asks for the common pitfalls — the mistakes and steps developers most often forget to implement — so explanations should call out likely bugs/omissions (missing guards, wrong ordering, forgotten side effects). Confidence: 0.7
- Brings in third-party/AI-generated bug reports (e.g. from another model) about their code and asks "are the bugs solved?" — expecting each claimed issue to be independently checked against the current source and answered with a per-item verdict (solved / partially / not solved) plus file:line evidence, rather than trusting the upstream report. Confidence: 0.75
- Wants deep bug hunts benchmarked against industry standards ("do find any other bugs here ... analyze deeply the industry standard code think and answer") — i.e. reason thoroughly first, then report concrete defects with file:line evidence, why it breaks, and how it should be done, rather than a superficial pass. Confidence: 0.7
- Prefers the agent to apply fixes directly to the code ("fix my code directly") rather than only proposing changes or asking for approval — expects the edits to actually be made. Confidence: 0.8
- Wants the diff always shown when code is changed ("always show the diff"). Confidence: 0.85
- Expects consistency across sibling/parallel code paths: if one money-mutating transaction checks `updateMany` counts and runs at Serializable isolation, every comparable path should do the same — flags a path that keeps Prisma's default isolation or ignores a write's row count as a real defect ("makes failure handling less consistent ... not fully race-safe"). Confidence: 0.65
- Cares about database-write concurrency safety as a standard, not a nicety — wants mutations to be explicitly race-safe (check the affected `count` after conditional writes, pick isolation levels deliberately) even when surrounding guards would "often avoid corruption". Confidence: 0.6
- Treats at least some of their projects as "for testing and learning purpose," so favors pragmatic, sandbox/free-tier setups (e.g. payment-gateway sandbox mode, simple hosting) over production hardening — advice should account for this learning-vs-production framing. Confidence: 0.5
- Deploys their projects on Vercel (serverless) and wants background/periodic work adapted to that model rather than re-architected away from it — e.g. turning an always-on `setInterval` worker into a protected HTTP endpoint driven by a `vercel.json` cron, and stretching time-based windows to fit the plan's cron cadence. Confidence: 0.55
- Works in a TypeScript/Express project bundled with tsup and deploys the `dist/` output to Vercel; expects build config (`vercel.json` `buildCommand`/`outputDirectory`) to be explicit so Vercel uses their bundler instead of compiling entrypoints with plain `tsc`, and expects an `export default app` handler bundled alongside the CLI entry. Confidence: 0.6
- For multi-step operational/setup work (e.g. deploying, wiring up config), wants to be walked through it as an explicit, ordered checklist of concrete actions — asks "what to do first, guide me step by step" and expects "do this first, then this" instructions rather than just a summary of what was changed. Confidence: 0.6
- Expects configuration/env documentation to be exhaustive — flags omitted variables ("why didn't you say the two SSLCOMMERZ_REQUEST_TIMEOUT_MS / ... in the variable section") and wants every relevant env var, including optional ones with their default values, listed rather than a curated subset. Confidence: 0.6
- Scopes fix work tightly and defers non-bug features: explicitly says which bugs to fix and which to exclude (e.g. "fix the bugs other than refund endpoints", planning to build refund endpoints later), and rejects edits that stray beyond the requested fix (denied adding a serializable-transaction retry helper). Keep each change targeted to the bug at hand and expect individual edits may be declined. Confidence: 0.6
- Tests their APIs with Postman (including against the deployed Vercel URL), so guidance for exercising endpoints should be framed in Postman terms (environments/variables, Bearer token setup, test scripts) rather than curl or code snippets; routinely asks for importable Postman collections targeting the deployed environment. Confidence: 0.6
- Thinks about money flows in lifecycle terms beyond "did it succeed" — asks how to reconcile an orphaned/stuck charge and turn it into a durable record that a future refund can act on, and whether the service already has code for it. When auditing existing code, wants both what exists (with file:line) and an explicit statement of the gaps/missing automation, plus concrete suggestions for what to add. Confidence: 0.65
- Re-asks the same underlying question until it is truly resolved ("but how can I know whether the money is deducted in this situation or not") — so a prior answer that covered the code fix but left the observability question implicit is not considered done. State plainly whether the app/database can answer it at all, which source of truth can (gateway API, dashboard), and name the missing capability. Confidence: 0.7
- When a payment/error state is ambiguous, wants both halves answered together: (a) how to determine ground truth from the gateway (validator API curl/SQL checks) and (b) how to reconcile the stuck record. Answers that only cover one, or that only explain theory, are insufficient — deliver the verification commands plus the code fix. Confidence: 0.7
- Values error paths that preserve diagnosability: expects the upstream HTTP status and response body to be captured into thrown errors instead of discarded behind a generic message, and expects the agent to justify *why* a state is safe to mark FAILED (why a later IPN still records the charge). Confidence: 0.65
- Expects verification after edits — runs `npx tsc --noEmit` (or equivalent) and re-reads the touched helper to confirm the new branch is actually reachable, rather than trusting the edit compiles alone. Confidence: 0.6
- Expects the agent to discover and reuse existing project artifacts before proposing to create new ones — pushed back with "I already have a postman collection, can't you find that?" when a listing reported an empty folder, and had to be reminded that directory listings can hide `.gitignore`d paths. Search the filesystem broadly (including ignored files) and work with what already exists rather than re-creating it. Confidence: 0.5

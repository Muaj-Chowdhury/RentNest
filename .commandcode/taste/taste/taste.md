# Taste
- Communicates by highlighting a specific symbol/line in the IDE and asking for a conceptual walkthrough (e.g. "explain X how does it work and the flow"), so prefers thorough, step-by-step explanations that trace the call flow and reference exact file:line locations rather than short one-line answers. Confidence: 0.8
- When asking about code, wants the full picture: distinct scenarios/branches, the data flow end-to-end, and the rationale for decisions (e.g. "what should each return carry and how do I know"), not just a description of what the code literally does. Confidence: 0.7
- Explicitly asks for the common pitfalls — the mistakes and steps developers most often forget to implement — so explanations should call out likely bugs/omissions (missing guards, wrong ordering, forgotten side effects). Confidence: 0.7
- Brings in third-party/AI-generated bug reports (e.g. from another model) about their code and asks "are the bugs solved?" — expecting each claimed issue to be independently checked against the current source and answered with a per-item verdict (solved / partially / not solved) plus file:line evidence, rather than trusting the upstream report. Confidence: 0.75
- Wants deep bug hunts benchmarked against industry standards ("do find any other bugs here ... analyze deeply the industry standard code think and answer") — i.e. reason thoroughly first, then report concrete defects with file:line evidence, why it breaks, and how it should be done, rather than a superficial pass. Confidence: 0.7
- Prefers the agent to apply fixes directly to the code ("fix my code directly") rather than only proposing changes or asking for approval — expects the edits to actually be made. Confidence: 0.8
- Wants the diff always shown when code is changed ("always show the diff"). Confidence: 0.85
- Expects consistency across sibling/parallel code paths: if one money-mutating transaction checks `updateMany` counts and runs at Serializable isolation, every comparable path should do the same — flags a path that keeps Prisma's default isolation or ignores a write's row count as a real defect ("makes failure handling less consistent ... not fully race-safe"). Confidence: 0.65
- Cares about database-write concurrency safety as a standard, not a nicety — wants mutations to be explicitly race-safe (check the affected `count` after conditional writes, pick isolation levels deliberately) even when surrounding guards would "often avoid corruption". Confidence: 0.6
- Scopes fix work tightly and defers non-bug features: explicitly says which bugs to fix and which to exclude (e.g. "fix the bugs other than refund endpoints", planning to build refund endpoints later), and rejects edits that stray beyond the requested fix (denied adding a serializable-transaction retry helper). Keep each change targeted to the bug at hand and expect individual edits may be declined. Confidence: 0.6
